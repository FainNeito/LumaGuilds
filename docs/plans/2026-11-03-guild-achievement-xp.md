# Guild achievement XP: design and acceptance boundaries

Status: design in progress. No runtime implementation or release approval is established by this document. User selected future completions only on 2026-11-03; previously completed achievements must not be paid retroactively.

## Context

Guild achievement progress and personal Minecraft XP are currently stored per player. Shared events may reach several members, so awarding guild XP for every personal completion would multiply the guild payout. Current bundled weekly quest defaults award 500, 1,500, 3,000, or 5,000 guild XP, with an additional full-set reward. Production configuration may differ.

## Requirements

- When an eligible achievement is earned, the system shall award a small, explicitly displayed amount of guild XP at most once per guild and achievement ID, regardless of member count, repeated events, reconnects, or player membership changes.
- Guild XP and its idempotency record must be durable and atomic within the existing progression store. A failure or restart between player-data persistence and guild-XP delivery must not silently lose the award or grant it twice; pending awards must retain their original guild and achievement identity.
- The existing experience transaction cleanup prunes old rows according to `progression.transaction_retention_days`; a deterministic ID in that table alone is not a permanent once-per-guild receipt. Use a durable achievement-specific ledger protected from that cleanup and commit it atomically with the award, or demonstrate an equivalent permanent mechanism before wiring payouts.
- Personal Minecraft XP, current advancement IDs, historical progress, quest rewards, prestige, and other XP sources must retain their existing semantics. Unavailable or ambiguous persistence shall fail closed and surface a recoverable/reviewable state.
- User decision 2026-11-03: prevent advancement-earned guild XP for members whose IP matches another member of the same guild, including previously seen IPs of offline members. Do not apply the restriction to personal Minecraft XP or other guild XP sources. Define when offline observations expire, how trustworthy client IPs are obtained through the actual proxy, and how missing, stale, changed, shared-proxy, IPv6 and reconnect observations are handled before wiring the rule. Unknown comparisons must not silently pass as unique. Store no raw IP addresses in guild XP receipts or logs; a keyed, access-controlled comparison mechanism needs review.
- For shared guild events involving several members, the rule must evaluate actual eligible participants and pay at most once if an eligible participant qualifies; the presence of one blocked member must not silently disqualify an unrelated eligible member. Do not allow timing or membership changes to convert an ineligible completion into an automatic later payout.
- Do not backfill existing completions or award XP merely because existing state is observed during initialization. Never infer that personal player state is complete guild-wide historical data. Selection of eligible events, deployment cutoff, configuration and cap semantics require design before integration.
- Proposed defaults: TASK 25, GOAL 50, CHALLENGE 100 guild XP; the root awards zero. Across the current 29 non-root nodes the proposed lifetime maximum is 1,725 XP per guild, before any explicitly defined bonus semantics. These figures are preliminary and must be compared against actual deployment configuration and abuse cases before release.
- The menu and advancement details must accurately distinguish personal Minecraft XP from guild XP; changes need the required interactive mobile-accessible preview and native-client acceptance.

## Verification to prepare

Prove duplicate member completions, replay, membership change, player save and database failures, ambiguous commit, retry, shutdown/restart, old data, privacy, and the chosen historical policy. Verify real SQLite and MariaDB atomic behavior, the production-compatible build, and existing XP/source-accounting contracts. Quest comparisons must use actual deployment configuration before balancing is finalized.

## Initial evidence

The focused `GuildAchievementXpPolicyTest` ran three tests successfully after supplying the companion API JARs used by the existing local integration checkout. The first attempt failed compilation because the clean worktree lacked those ignored local dependencies; no test ran on that attempt. The policy is not connected to advancement delivery, and these tests do not establish award persistence, future-only behavior, multi-member handling, or MariaDB compatibility.

The isolated SQL prototype adds a permanent guild-and-achievement receipt in the same transaction as XP and ordinary history. Its focused SQLite repository and policy suites passed after adding regression cases for history pruning, rollback on ledger-insert failure, and simultaneous requests from multiple members. This is not wired to the runtime or an upgrade migration; MariaDB, actual restart, cutover/backfill, lifecycle publication, and end-to-end delivery remain unverified. An initial compilation attempt exposed missing exhaustive `ACHIEVEMENT` source mappings; those mappings were added before the successful test run.

After the user's same-IP decision, an isolated opaque-observation comparison policy and three focused tests were added. They cover a matching offline peer, distinct known peers, and missing/invalid membership. They do not collect IPs or prove proxy forwarding, secure offline persistence, retention, or end-to-end payout eligibility. No runtime integration or deployment is claimed.

The next isolated prototype adds HMAC-SHA256 comparison tokens and a SQLite-tested offline observation repository. Focused tests pass for keyed token separation, placeholder-address rejection, offline observation recreation, stale-update ordering, and rejection of raw IP text. A key-generation marker makes mismatched-key observations unavailable, and conflicting same-timestamp observations become ambiguous until a newer observation is available. It is not wired to login or rewards and has not been tested against MariaDB. Trusted proxy forwarding, secret-key generation/storage/rotation and backup, staleness/retention, upgrade migrations, and cutover behavior remain unresolved. The prototype must remain disabled until these are addressed.

An isolated completion coordinator prepares a bounded, deterministic intent only for an explicitly new event with known nonmatching member observations; it rejects historical, shared-address, and unknown-address snapshots before invoking the sink. Intent replay validates the original guild, achievement definition, amount and transaction ID. A SQLite integration test exercises this coordinator against the real permanent award ledger, including duplicate member completion. The completion-time event flag and snapshot are caller supplied; proxy verification and actual crash-durable delivery remain unverified. The prototype SQL sink does not publish level-up events and must not be used at runtime until that is fixed.

An isolated strict JSON codec serializes completion-time intents without IP data and rejects malformed, duplicate, noncanonical and tampered fields. Its focused tests pass. Serialization alone is not durable delivery or restart proof.

The local runtime prototype now writes eligible pending intents in the same player-data JSON as achievement progress and personal XP, retries them on initialization and periodic processing, and removes them only after awarded/duplicate results. Startup synchronization is marked historical; true listener events are explicitly marked new, and an initial stall observation cannot pay for an existing stall. MockBukkit tests cover player-data-container recreation, including a player leaving the original guild before retry, and assert personal XP is not paid twice. These are mocks, not actual restart or crash-atomicity evidence.

The optional bridge remains unbound and disabled. Its current preparation error/unknown-address path does not preserve a reviewable unpaid intent, so it must not be enabled. Trusted IP forwarding, key provisioning/backup, stale offline addresses, persistent review or safe failure semantics, actual player-save crashes, level-up publication, SQLite and MariaDB migrations, and end-to-end client tests remain release blockers. Continuous playtime and observed stall transitions need explicit future-only acceptance tests. The prototype is not production-ready.

The isolated future-only event routing now defaults observations to historical, explicitly marks genuine listener events as new, and treats the first stall observation as a baseline. Focused MockBukkit tests cover a later unowned-to-owned stall transition, a pending reward replay after runtime recreation and guild departure, historical suppression, rejection of a wrong-guild intent, and malformed outbox quarantine. These tests pass but do not simulate a process crash or verify real player.dat durability. The address bridge tests use synthetic snapshots, not actual network or proxy addresses. Future-only playtime transition and all remaining blockers above still require verification.

Unknown-address and eligibility exceptions now retain an unpayable review marker alongside the player's achievement data. A focused runtime test verifies that the marker survives mocked runtime recreation, personal XP is still delivered, and the marker is not automatically paid. The marker contains no IP data, but has no staff review interface, timestamp, or verified real player-data crash durability; it does not prove eligibility and cannot safely be paid from later IP observations. The earlier statement that no reviewable marker exists is superseded by this prototype. The bridge remains disabled and all other blockers still apply.

Review found that personal advancement completion cannot serve as a guild-level progress ledger, and a player's initialized flag cannot establish that a different guild's playtime was newly earned. Both require durable guild-scoped tracking and a reliable event/cutover model before enabling rewards. The address repository retains only the last observation, not address history; retention and comparisons must be designed and verified before satisfying the offline-member protection requirement.

As a conservative safeguard, sampled playtime totals are now always treated as historical for guild XP. Personal advancement progress remains active; guild XP for playtime is intentionally unavailable until event-backed guild tracking can prove a future completion. This prevents the known false-positive route but does not implement the desired playtime reward.

An isolated port of the ten draft commits onto parent main 3d76a629 compiled and passed the focused runtime, boss, SQL award and icon tests. The histories diverge; this port does not reconcile the fork's unrelated changes or authorize replacing fork main.

The pure eligibility policy can now compare the actor's current fingerprint to a complete retained peer history and fails closed for incomplete histories. Its focused tests pass, including a match against an older offline observation. This policy is not wired to the bridge: durable history collection, explicit completeness and retention semantics, key lifecycle and migration remain required before it is safe to use.

An isolated guild-scoped progress repository records event IDs, progress and completion rows in one SQL transaction. SQLite tests cover separate guilds, replay, conflicting event reuse, concurrent duplicate delivery, repository recreation, absent guilds, and rollback when completion insertion fails. It is not wired to gameplay or payout and its completion rows do not contain an eligibility snapshot: they must never be interpreted as permission to award XP. Still required: canonical event IDs and one-event-per-guild routing, future-only cutover, actor and trusted address evidence captured atomically, lifecycle and schema migration, retention, MariaDB concurrency, crash/restart and integration acceptance. Unknown or removed definitions fail closed; a compatible definition migration policy is required.

The repository now exposes an inspection-only completion read that validates the associated stored event and fails closed on missing or invalid event data. A pure helper derives stable event IDs from an authoritative source UUID, guild and requirement. Focused SQLite tests verify inspection after repository recreation, rejection of an orphaned completion and idempotent replay of a derived event ID. This does not establish a live source contract, actual process-restart durability, or eligibility to pay; high-frequency events without authoritative durable IDs still need a safe design.
